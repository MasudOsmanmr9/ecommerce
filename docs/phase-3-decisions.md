# Phase 3 decisions

This document records the design decisions made for Phase 3 (domain model). Each decision explains why it was chosen, alternatives considered, and trade-offs.

1) UUID primary keys
- Decision: All new business entities use UUID primary keys generated by PostgreSQL (gen_random_uuid()).
- Why: UUIDs are safe for distributed systems, are unguessable, and simplify data merging between systems and offline creation.
- Alternatives: Auto-increment integer PKs. Rejected because sequential IDs are guessable and make replication/merging more complex for distributed clients.
- Trade-offs: Larger storage and index size; potential index bloat. This project accepts the cost for the benefit of distribution and security.

2) Soft delete for users
- Decision: Users include deleted_at (soft delete) and email uniqueness is enforced only for active users via a partial unique index.
- Why: Soft delete preserves historical references to users and prevents accidental loss of audit/history.
- Alternatives: Hard delete and cascading deletes. Rejected because historical data and auditability are important for orders and redemptions.
- Trade-offs: Query logic must filter deleted_at IS NULL for active-user checks.

3) Relations and ownership
- Decision: Business FKs reference user_id (UUID). Entities reference owners by ID, not by email.
- Why: Email is mutable and not a stable ownership key; user_id is stable and the canonical owner identifier.

4) Cart and CartItem
- Decision: Carts can be associated with a user or be anonymous (user_id nullable). CartItems enforce uniqueness on cart+variant.
- Why: Support guest carts and prevent duplicate items in the same cart.

5) Inventory per Variant
- Decision: Inventory is modeled per ProductVariant with a one-to-one mapping to the inventory row. Inventory quantity is an integer and is stored in its own table.
- Why: Separating inventory allows inventory-specific attributes, pooling, and future multi-location extension.

6) Partial indexes and constraints
- Decision: Partial unique index on users(email) where deleted_at IS NULL to allow reusing email addresses for users that were deleted while preventing active duplicates.
- Why: Real-world email reuse scenarios and account lifecycle management.

7) Migrations-only schema changes
- Decision: synchronize=false and all schema changes are applied through TypeORM migrations.
- Why: Production safety and controlled schema evolution.

8) Money storage
- Decision: Prices and monetary amounts are stored as integer cents (bigint) to avoid floating point arithmetic errors.
- Why: Accurate money math and sorting without precision loss.

For each decision above, the codebase contains concrete implementations and the migration applies the schema. If you want more depth for any decision (e.g., index choices, partitioning, audit tables), request the specific topic and a deeper write-up.

## Database Schema: Relations & Indexes

### Entity Relationships

#### User-Centric Relations
- **User → Order** (1-to-Many): User can have multiple orders. Orders can be orphaned (SET NULL on user delete).
- **User → Cart** (1-to-Many): User can have multiple carts. Carts can be orphaned (SET NULL on user delete).
- **User → CouponRedemption** (1-to-Many): User can redeem multiple coupons. Redemptions cascade-deleted on user delete.
- **User → Address** (1-to-Many): User can have multiple addresses.

#### Product Hierarchy
- **Product ↔ Category** (Many-to-Many): Products belong to multiple categories via `product_categories` join table.
- **Product → ProductVariant** (1-to-Many): Each product has variants (size, color, etc.). Variants cascade-deleted on product delete.
- **ProductVariant → Inventory** (1-to-1): Each variant has exactly one inventory record. Inventory cascade-deleted on variant delete.

#### Transactional Relations
- **Cart ↔ CartItem** (1-to-Many): Cart contains multiple items. Items cascade-deleted on cart delete.
- **CartItem → ProductVariant** (Many-to-1): Multiple cart items can reference the same variant, but each cart-variant pair is unique. Variant deletion RESTRICTED (prevents deleting variants in active carts).
- **Order ↔ OrderItem** (1-to-Many): Order contains multiple items. Items cascade-deleted on order delete.
- **OrderItem → ProductVariant** (Many-to-1): Multiple order items reference variants. Variant deletion RESTRICTED (prevents deleting variants from order history).
- **Order → Payment** (1-to-Many): Order can have multiple payment attempts. Payments can be orphaned (SET NULL on order delete).

#### Coupon Relations
- **Coupon → CouponRedemption** (1-to-Many): Coupon can be redeemed by multiple users. Redemptions cascade-deleted on coupon delete.
- **CouponRedemption → User** (Many-to-1): User can redeem multiple coupons.
- **CouponRedemption → Coupon** (Many-to-1): Each redemption links one user to one coupon.

#### Payment Processing
- **Order → Payment** (1-to-Many): Track multiple payment attempts per order.
- **Payment → PaymentAttempt** (1-to-Many): Track detailed attempt logs for each payment.
- **Order → Refund** (1-to-Many): Refunds associated with orders.

### Indexes

#### Unique Constraints (Prevent Duplicates)

| Index Name | Table | Columns | Type | Purpose |
|---|---|---|---|---|
| `uq_users_email_active` | users | email | Partial Unique | Allow email reuse for deleted users only; enforce uniqueness for active users (deleted_at IS NULL) |
| `uq_product_variants_sku` | product_variants | sku | Unique | Prevent duplicate SKUs across all product variants |
| `uq_cart_item_cart_variant` | cart_items | cart_id, product_variant_id | Unique | Prevent duplicate items in the same cart |
| `uq_coupon_redemptions_coupon_user` | coupon_redemptions | coupon_id, user_id | Unique | Prevent the same user redeeming the same coupon twice |

#### Check Constraints (Data Integrity)

| Table | Constraint | Purpose |
|---|---|---|
| cart_items | `quantity > 0` | Quantities must be positive |
| order_items | `quantity > 0` | Quantities must be positive |
| inventory | `quantity >= 0` | Inventory cannot go negative |

### Foreign Key Cascade Strategy

| Scenario | Delete Behavior | Rationale |
|---|---|---|
| Delete User | Cart/Order set to NULL | Preserve order/cart history; decouple from user |
| Delete Product | ProductVariants cascade | Variants tied to specific product |
| Delete ProductVariant | Inventory cascades; OrderItem/CartItem RESTRICT | Prevent deletion while in active carts or historical orders |
| Delete Cart | CartItems cascade | Items only exist within a cart |
| Delete Order | OrderItems cascade; Payments set to NULL | Items tied to order; payments preserved for audit |
| Delete Coupon | CouponRedemptions cascade | Redemptions tied to specific coupon lifecycle |

### Index Strategy Rationale

1. **Partial Index on Users Email**: Allows recycling deleted user emails in production without violating uniqueness.
2. **SKU Uniqueness**: Guarantees product variant identity across system; enables lookup by SKU.
3. **Cart Item Uniqueness**: Prevents accidental duplicate items; enforces cart integrity.
4. **Coupon Redemption Uniqueness**: Prevents coupon abuse; one redemption per user per coupon.
5. **Quantity Checks**: Prevent invalid states at database layer (defense-in-depth).
6. **RESTRICT on Variant Deletes**: Protects data integrity by preventing deletion of variants referenced in active carts or order history.
